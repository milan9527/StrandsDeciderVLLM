# HTTP 清理修复后的并发复测

[English](CONCURRENCY_RETEST.md) | 简体中文

本文记录较早的一轮测试，当时结束后恢复为 8 请求准入。后续 [1–128 测试](CONCURRENCY_128.zh-CN.md) 提高并保留了服务限额，其中一项数值阈值异常单独记录。

**2026-10-13：正式请求 5,200/5,200 次成功，包含 16、32 并发。** 没有 HTTP 失败或推理超时；所有成功响应的候选选择与原版一致，数值差异满足原有 0.02 阈值。这是短时稳定性结果；更高并发仍增加了延迟，没有提升吞吐量。

## 实测结果

通过实际 [公网 HTTPS 地址](https://d1e9udi8st2p3g.cloudfront.net) 调用现有按需 `g6.xlarge` / NVIDIA L4。下表测试期间，引擎、问题和 HTTP 并发上限均临时设为 32，速率上限提高至每秒 200 次、突发容量 64，避免正常的每秒 20 次限流决定测试结果。

首轮，每个并发档位 400 次：

| 并发 | 成功 / 请求数 | 次/秒 | 平均 ms | P50 ms | P95 ms | P99 ms |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 400/400 | 18.52 | 53.9 | 53.3 | 58.3 | 61.0 |
| 4 | 400/400 | 32.08 | 124.4 | 123.6 | 132.0 | 134.1 |
| 8 | 400/400 | 36.04 | 220.7 | 220.3 | 228.4 | 254.9 |
| 16 | 400/400 | 29.60 | 539.0 | 539.7 | 549.2 | 559.4 |
| 32 | 400/400 | 30.71 | 1015.9 | 1034.7 | 1050.3 | 1130.9 |

相同配置延长复测，每档 800 次：

| 并发 | 成功 / 请求数 | 次/秒 | 平均 ms | P50 ms | P95 ms | P99 ms |
|---:|---:|---:|---:|---:|---:|---:|
| 8 | 800/800 | 33.32 | 239.7 | 241.0 | 245.9 | 254.8 |
| 16 | 800/800 | 30.95 | 515.4 | 515.6 | 538.2 | 571.4 |

另做了一组对照，保留部署时的引擎 / 问题 / HTTP 上限 8，仅提高速率限制：8 并发的 400/400 次请求成功，达到 **34.16 次/秒，P95 239.7 ms**。

## 结论

- 16、32 并发在两轮中均成功完成，本轮没有复现之前的超时。
- 延长复测中，8 并发达到 **33.32 次/秒、P95 245.9 ms**。在当前配置下，提高并发主要增加了等待时间。
- 服务上限设为 8，依据是延迟与吞吐量的取舍；不能据此认为 vLLM 无法处理更多并发请求。
- 本轮不能证明 [历史基准](GPU_CONCURRENCY.zh-CN.md) 中 5 次超时的全部原因，也不能作为长期稳定性保证。

服务已恢复为 **8 并发、原有每秒 20 次令牌桶**，突发容量 16。临时测试限额已撤销，不能将压测中的处理能力当成默认公网 API 的持续速率限额。

## 测试方法与范围

保持相同的部署镜像、v19 权重、GPU、8192 批次 token 预算、4096 上下文窗口、0.7 GPU 显存比例及 25 秒推理超时。Prefix caching、chunked prefill 和 CUDA Graphs 继续关闭，没有新增 GPU 实例。

输入来自四个支付场景，每场景五步，共 20 个输入，每次 304–445 token。各档位等次数重复每个输入。客户端位于 GPU 实例之外，以固定并发 worker、HTTPS 连接复用、40 秒客户端超时进行闭环压测，不自动重试。本轮侧重每次请求包含一个问题的决策调用。

每个档位先预热 `max(20, 2 × 并发数)` 次。共 **312 次预热请求** 单独保存，不计入延迟和吞吐统计。吞吐量按正式请求整体耗时计算，延迟分位数取成功请求的 nearest-rank。保留了原始响应、状态码、请求 ID、服务端与客户端耗时及逐响应对比。

请求数分别为：引擎上限 8 的对照 800 次，引擎上限 32 的首轮 2,000 次，延长复测 2,400 次。相对原版的最大概率绝对差为 **0.0150**，最大置信度差为 **0.0200**。这验证适配后的行为一致性，不代表业务判断准确率。

历史基准是在限制 CPU / 内存的 g6.4xlarge 上通过回环 HTTP 测量；本轮在 g6.xlarge 上通过公网 HTTPS 测量。应比较本轮内部的并发档位，不合并两批数据。

## 复现与记录

使用 [benchmark_service.py](../scripts/benchmark_service.py) 前，须主动配置服务端测试限额。`--engine-seqs` 只记录预期配置，不会修改服务端。本轮另行保存了实际容器启动参数，核实配置。

```bash
uv run --no-sync python scripts/benchmark_service.py \
  --credentials .deployment/api-credentials.json \
  --engine-seqs 32 --label engine-32-repeat \
  --levels 8 16 32 --requests 800 \
  --output artifacts/concurrency-retest-new
```

操作时使用临时 systemd 覆盖配置和 25 分钟自动恢复定时器。测试后启动参数与原值完全一致，覆盖配置已删除，健康检查恢复。修改在线服务前请阅读 [运维说明](../deployment/README.zh-CN.md)。
