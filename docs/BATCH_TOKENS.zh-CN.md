# 批次 token 预算测试

[English](BATCH_TOKENS.md) | 简体中文

2026-10-13。在相同的按需 EC2 `g6.xlarge` / NVIDIA L4 上，仅改变 `max_num_batched_tokens`，测试 8192、16384、32768。引擎序列上限始终为 128，HTTP / 问题准入始终为 256。

正式请求 **23,040/23,040** 成功，HTTP 失败 **0** 次，候选选择变化 **0** 次。数值对齐通过 **23,040/23,040** 次；概率和置信度的绝对差阈值保持 0.02。另有 **1,948** 次预热，失败 **0** 次，不计入性能数据。

**本轮未观察到扩大批次预算带来的吞吐提升，建议保持 8192。** 16–128 并发仍在约 30 次/秒。128 并发的 P95 从 8192 基线的 4.93 秒，变为 32768 下的 5.98 秒；32768 复测为 5.90 秒。8 并发单轮数据有波动，不能把其中的百分比变化解释为已确认的参数因果效应。

## 如何理解

32768 足以容纳 64 条当前最长输入：`64 × 445 = 28480` token；64 并发仍约 30 次/秒，说明放宽预算并没有消除当前吞吐平台。更大的预算只是允许调度器安排更多 token，不会强制形成满批，也不会增加 GPU 算力。

本轮没有做内核或 CPU 性能剖析，因此没有把瓶颈归因于某一个内核、内存带宽或 CPU 环节。后续应先分析实际批次大小和 GPU / CPU 时间分布，再评估 CUDA Graphs 等适配优化。前缀缓存和分块预填充受当前完整 prefill 实现约束，不能直接打开。

## 测试方法

- 每种预算依次测试 8、16、32、64、128 并发；32768 在 32、64、128 并发各复测一次。
- 每档 1,280 次正式请求；四场景 × 五个独立选择题，共 20 条输入，每条恰好重复 64 次。输入与原版参考记录逐条核对一致。
- 每请求一个问题，实际输入 304–445 token，平均 373.9 token。每个场景的业务事实固定；不执行支付，不把上一步答案写回后续输入。
- GPU 主机外的固定数量异步 worker 通过公网 HTTPS 调用；收到完整响应后发下一次请求，复用连接，无自动重试。每档预热 `max(20, 2 × 并发数)` 次。
- 客户端延迟包含网络、排队和推理；服务端耗时另行保留。吞吐为成功请求数 / 正式阶段总耗时，P50/P95/P99 使用成功响应的 nearest-rank。
- vLLM 0.31.0、模型镜像和权重、BF16 底座 / FP32 Pointer Head、4 vCPU / 14 GiB 容器、4096 上下文、0.7 显存比例均不变。关闭前缀缓存、分块预填充、CUDA Graphs；每分钟速率阈值 120,000、突发 512，服务端 / 客户端超时 25 / 40 秒。
- 每次响应与固定原版结果核对候选 ID、概率和置信度。适配一致性不等于业务准确率；数值超阈值保留在原始审计中，不放宽阈值。

8192 / 16384 / 32768 是每批调度 token 预算，不是单条输入长度。在当前平均输入下，粗略对应约 21 / 43 / 87 条完整输入；实际组成由调度器决定。这是固定短输入的容量测试，不能外推到长上下文或长期可用性。

## 服务状态与证据

测试后已恢复 **8192 token 批次预算**，保留引擎 **128**、HTTP / 问题准入 **256**。恢复后的启动参数与测试前一致；GPU 常驻运行。
